# 第一章 · MOODAY 的使命（Mission）

## 1.1 MOODAY 是什么

**MOODAY V4 不是一个普通照片编辑器，而是一套以“情感、艺术、实体成品”为核心的照片创作平台。**

它的目标不是让用户学习修图，而是让任何普通人只需要一张手机照片，就能制作出具有纪念价值、礼物价值和收藏价值的高品质作品。

MOODAY 创造的不是图片，而是回忆。

---

## 1.2 服务对象

MOODAY 当前主要面向 **韩国市场**，所有产品设计、UI、排版、氛围、风格、审美都以韩国用户的使用习惯和审美偏好为第一标准。

默认语言：

* 한국어（默认）
* 中文
* English

整个系统采用三语言词典，任何页面都不得写死文字。

---

## 1.3 产品设计理念

MOODAY 的核心理念：

* 简单，不让用户学习复杂修图
* 一键，让复杂算法隐藏在系统内部
* 艺术，让普通照片拥有高级视觉效果
* 成品，一切设计围绕最终打印效果，而不是屏幕效果

所有风格、氛围、模板、版式，均以韩国流行审美为主要设计方向。

---

## 1.4 当前产品（第一阶段）

当前 V4 首批产品：

1. 相纸相框
2. 艺术纸相框
3. 魔镜灯光画
4. 证件照
5. 免费头像
6. 免费壁纸

其中，**魔镜灯光画** 为当前可直接生产的核心产品，也是第一阶段优先完成完整业务流程的产品。

第一阶段目标不是产品数量，而是打通完整流程：

上传照片 → 编辑 → 预览 → 提交 → 下单 → 发货

---

## 1.5 第二阶段规划（已预留）

未来扩展产品：

* 3D 光栅立体画
* 亚克力小夜灯
* 多层景深亚克力画
* 裸眼 3D 图像

以上产品将在 V4 架构成熟后接入，不重新开发编辑器，只新增产品配置与产品模块。

---

## 1.6 开发原则

MOODAY 采用 **一个编辑器，多产品** 的架构。

不同产品共用同一套底层系统，根据产品配置自动切换功能，而不是维护多套编辑器。

这也是 MOODAY V4 最核心的长期架构思想。

# 第二章 · 工程架构（Project Architecture）

## 2.1 架构目标

MOODAY V4 采用 **一个编辑器，多产品** 的架构。

所有产品共用同一套底层系统，不允许为不同产品重复开发编辑器。

产品之间的区别，只能通过 **Config（配置）** 控制，而不是复制页面或复制代码。

---

## 2.2 顶层目录职责

```text
mooday-editor-V4/

assets      素材资源
config      配置中心
core        底层引擎
modules     功能模块
pages       页面
state       状态中心
```

六个一级目录为永久结构，未经确认不得新增、删除或改名。

---

## 2.3 六大目录说明

### assets（素材资源）

存放图片、图标、字体、模板、产品体验默认图片。

不得存放业务代码。

### config（配置中心）

存放所有可修改的数据。

例如：

* 产品配置
* 三语言词典
* 布局尺寸
* 颜色主题

任何模块不得写死数据，必须读取 Config。

### core（底层引擎）

负责底层能力：

* Canvas
* Render
* Touch
* Export
* Worker API

Core 不负责业务逻辑。

### modules（功能模块）

每个模块只负责一个功能。

例如：

* Upload
* Mood
* Style
* Decoration
* Clarity
* Optimize
* Preview
* Submit

模块之间禁止直接修改彼此的数据。

### pages（页面）

Pages 只负责用户看到的界面。

不得处理业务逻辑。

页面通过调用 Modules 完成功能。

### state（状态中心）

整个网站运行状态唯一入口。

包括：

* 当前产品
* 当前页面
* 当前图片
* 编辑状态

任何运行数据统一进入 State，不允许多个模块各自保存状态。

---

## 2.4 冻结原则

本目录结构为 **Freeze v1.0**。

禁止出现以下情况：

* 文件改成文件夹
* 文件夹改成文件
* 同职责建立两个目录
* 同功能建立两个模块

所有新增内容，必须在现有架构内扩展，而不是重新建立目录。

# 第三章 · 开发原则（Permanent Rules）

> 本章为 MOODAY V4 永久规则，未经确认不得修改。

## 3.1 职责唯一原则

一个模块，只负责一个职责。

例如：

| 模块         | 唯一职责 |
| ---------- | ---- |
| Upload     | 上传照片 |
| Editor     | 图片编辑 |
| Mood       | 氛围   |
| Style      | 风格   |
| Decoration | 装饰   |
| Clarity    | 清晰   |
| Optimize   | 优化   |
| Preview    | 产品预览 |
| Submit     | 提交订单 |

禁止一个模块同时负责多个业务。

---

## 3.2 禁止跨模块

任何模块不得直接修改其它模块的数据。

正确流程：

页面 → 模块 → State → RenderEngine

禁止：

* Mood 修改 Style
* Upload 修改 Order
* Preview 修改 Submit

所有数据统一经过 State。

---

## 3.3 禁止跨层调用

工程固定四层：

UI（Pages）

↓

Modules

↓

State

↓

RenderEngine

规则：

* 页面不能直接修改 State。
* 页面不能直接调用 Render。
* 模块不能互相调用。
* RenderEngine 是唯一渲染入口。

---

## 3.4 禁止写死数据

MOODAY 必须支持：

* 手机
* 平板
* 横屏
* 竖屏
* 不同尺寸设备

因此：

禁止写死：

* 固定宽度
* 固定高度
* 固定按钮位置
* 固定屏幕尺寸

所有尺寸必须来自 Config，并由系统实时计算。

---

## 3.5 V3 遗产继承原则（永久）

V4 不继承 V3 的代码结构，但必须继承 V3 已验证的经验。

开发任何功能前，必须优先参考 V3：

* README
* PRODUCT_SPEC
* 已验证源码
* 成熟算法
* 踩坑经验

原则：

> **继承经验，不复制架构。**

禁止因为重构 V4 而丢失 V3 已验证的成熟逻辑。

---

## 3.6 统一文件头规范（永久）

所有源代码文件必须使用统一文件头。

文件头必须包含：

* File（文件名）
* Path（完整路径）
* 功能（负责什么）
* 不负责（禁止什么）
* 依赖（允许依赖哪些模块）

任何新增文件不得省略文件头。

---

## 3.7 面向非程序员原则

MOODAY 项目负责人不以程序员方式开发。

因此所有开发指导必须遵守：

* 写完整文件路径
* 优先提供全文替换
* 不要求用户寻找第几行
* 使用中文说明职责
* 修改前明确说明影响范围

任何 AI 必须按照以上方式协助开发，不得使用仅程序员才能理解的表达方式。

---

## 3.8 每日开发日志（永久规则）

MOODAY V4 开发期间，每天开发结束必须自动生成一份 **《MOODAY V4 开发日志》**。

**无需用户提醒，只要用户表达开发结束，即立即生成。**

触发示例（包括但不限于）：

* 今天结束了
* 开发结束
* 收工
* 今天做到这里
* 今天就这样
* 明天继续

以上均自动触发开发日志。

---

### 输出格式（强制）

开发日志必须使用 **Writing Block（一键复制）** 输出，方便直接追加到 `DEV_LOG.md`。

必须包含完整日期，例如：

**2026-08-23（星期日）**

不得省略日期。

---

### 开发日志固定结构

#### ① 今日完成

今天真正完成的开发内容。

不得虚构未完成项目。

#### ② 今日确定

今天正式确定的规则、架构、流程、命名、产品逻辑。

以后发生冲突，以开发日志记录为准。

#### ③ 今日踩坑（必须）

记录今天发现的问题与原因，例如：

* 为什么不能这样设计
* 放弃了哪个方案
* 哪个命名容易混乱
* 哪个架构以后禁止再犯

所有踩坑经验必须保留。

#### ④ 明日容易忘记（重点）

凡是今天讨论过、第二天可能忘记的事项，必须记录。

宁可多写，也不能遗漏。

#### ⑤ 下一步计划

只写下一步真正要开发的内容。

禁止填写大量未来计划。

---

### 永久要求

* 自动生成（无需提醒）
* 必须带日期
* 必须为一键复制格式（Writing Block）
* 可直接追加到 `DEV_LOG.md`
* 每日一条，不覆盖历史记录

# 第四章 · 命名规范（Naming Convention）

> 本章为 MOODAY V4 官方命名规范，全项目统一执行。

## 4.1 命名原则

MOODAY V4 全项目统一使用 **lowerCamelCase（小驼峰）**。

示例：

| 正确            | 错误             |
| ------------- | -------------- |
| upload        | Upload         |
| renderEngine  | RenderEngine   |
| appState      | app_state      |
| productConfig | Product_Config |

禁止混用：

* PascalCase
* snake_case
* kebab-case

整个项目保持唯一风格。

---

## 4.2 一个功能，一个官方名称

一个功能只能有一个名称。

禁止使用近义词。

例如：

| 官方名称       | 中文   |
| ---------- | ---- |
| upload     | 上传   |
| mood       | 氛围   |
| style      | 风格   |
| decoration | 装饰   |
| template   | 图文模板 |
| clarity    | 清晰   |
| optimize   | 优化   |
| preview    | 预览   |
| submit     | 提交   |
| order      | 订单   |

禁止出现：

* uploadPhoto
* imageUpload
* enhance
* improve
* photoPreview

所有功能统一采用官方名称。

---

## 4.3 Render 唯一原则

全项目只有一个 Render。

唯一名称：

`renderEngine`

禁止出现：

* render.js
* imageRender
* styleRender
* renderCanvas

所有渲染统一进入 `renderEngine`。

模块负责处理数据，不负责渲染。

---

## 4.4 文件命名原则

文件名必须能够直接表达职责。

例如：

```text
appConfig.js
layoutConfig.js
languageConfig.js

appState.js
editorState.js

renderEngine.js
canvasEngine.js
touchEngine.js
```

禁止同职责出现两个名称。

---

## 4.5 三语言词典原则

整个项目所有文字必须来自：

`config/languageConfig.js`

页面不得直接写：

* 韩文
* 中文
* 英文

统一通过词典读取。

任何新增文字，必须先进入词典，再进入页面。

---

## 4.6 禁止浏览器保留词

文件名、变量名、模块名不得使用浏览器或 JavaScript 保留名称。

例如：

* event
* window
* document
* name

必须使用具有业务含义的名称，避免产生冲突。

# 第六章 · 模块职责（Module Responsibility）

负责：

* 当前编辑状态

不负责：

* 氛围算法

* 上传

---

## 6.5 mood（氛围）

负责：

* 氛围效果

* 色彩氛围

不负责：

* 清晰
* 优化

---

## 6.6 style（风格）

负责：

* 艺术风格
* 画面表现
* 风格模板

不负责：

* Mood
* 清晰

Mood 与 Style 永远分离。

---

负责：

* 线条框
* 角框
* 角花
* PNG 装饰元素

不负责：

实体相框。

Decoration 是照片上的装饰，不是产品相框。

---

## 6.8 template（图文模板）

负责：

* 图文版式
* 标题排版
* 文字模板

## 6.9 clarity（清晰）

负责：

不负责：

* 阴影
* 色彩优化
* 肤色自然化

不负责：

* 去噪
* 锐化
* 去模糊

一句话：

> **优化 = 修色彩。**

---

## 6.11 preview（产品预览）

负责：

* 相框选择
* 纸张选择
* 产品规格
* 场景预览
* 实时预览

不负责：

照片编辑。

Preview 只负责成品展示。

## 6.12 submit（提交）

负责：

* 提交订单

Submit 不负责订单验证。

订单验证永远属于 Order。

## 7.6 编辑状态隔离原则（State Isolation）

MOODAY V4 所有产品必须保持 **编辑状态完全独立**。

### 一、Mood 与 Style 可叠加

进入编辑页时：

默认状态：

* Mood = 原图
* Style = 原图

因此，刚进入时图片不会发生任何变化。

用户可分别选择：

* Mood（氛围）
* Style（风格）

两者互不影响，可自由叠加。

例如：

原图

↓

选择「电影氛围」

↓

再选择「胶片风格」

最终效果 = **电影氛围 + 胶片风格**

如果后来把 Style 改回「原图」：

最终效果 = **电影氛围仍然保留**

同理：

如果把 Mood 改回原图：

则只取消氛围，Style 保留。

> Mood 与 Style 永远独立计算，不允许互相覆盖。

---

### 二、不同产品互不影响

每个产品拥有自己的编辑状态。

例如：

* 相纸相框
* 艺术纸相框
* 魔镜灯光画
* 证件照

它们之间不得共享：

* 图片
* Mood
* Style
* 装饰
* 模板
* 编辑记录

例如：

在魔镜灯光画修改了氛围，

不得影响相纸相框中的照片。

每个产品进入编辑器时，都必须初始化自己的独立 State。

> **一个产品一个 State，互不干扰。**

# 第八章 · 前后端架构（Cloud Architecture）

> MOODAY V4 采用 GitHub + Cloudflare 的统一架构。

## 8.1 架构组成

整个系统固定四层：

GitHub（前端）

↓

Cloudflare Worker（业务接口）

↓

Cloudflare R2（图片存储）

↓

用户订单（订单系统）

四层职责永久固定，不允许跨层开发。

---

## 8.2 GitHub（前端）

负责：

* 页面
* UI
* 编辑器
* Canvas
* 用户交互
* 三语言显示

不负责：

* 保存订单
* 图片存储
* 数据库
* 文件管理

GitHub 只负责用户看到的一切。

---

## 8.3 Cloudflare Worker

Worker 是唯一业务入口。

负责：

* 订单验证
* 提交订单
* 上传图片
* 调用 R2
* 返回数据

页面不得直接访问 R2。

所有请求必须经过 Worker。

---

## 8.4 Cloudflare R2

R2 只负责图片存储。

负责：

* 原图
* 最终作品
* 产品图片
* 用户上传图片

R2 不负责业务逻辑。

---

## 8.5 页面通信原则

唯一允许的数据流程：

页面

↓

Modules

↓

Worker API

↓

R2

禁止：

* 页面直接上传 R2
* 页面直接读取数据库
* Module 直接访问 R2

所有云端操作统一进入 Worker。
